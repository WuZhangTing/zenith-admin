## 1. 结论

清库后重新初始化的环境中，支付中心目录 20 个页面均能加载，主要管理动作和跨页面支付业务闭环已用内置浏览器重新验证。沙箱已跑通：

- 手工下单、支付成功回调、回调日志、事件派发和双分录台账；
- 小额退款、大额退款审批通过/驳回、投诉退款并完结；
- 自动分账、手工分账、分账冲正、转账预占与四眼驳回；
- 结算批次生成、余额不足保护、补足余额后结算、标记到账；
- 沙箱自动对账、差异挂账归档；
- 风控拦截、人工审核放行/拒绝；
- 预授权冻结、部分转支付、余款解冻；
- 一次性公开支付链接、支付次数限制、Token 轮换；
- 会员钱包充值退款冲正、连续包周首扣/续扣/关闭自动续费；
- 业务支付接入示例 `pending → paying → paid` 和自动履约。

本轮未发现新的 P0 资金越权或重复出款现象。此前基线中发现的回调身份/金额校验、租户范围、结算幂等、未知结果、统一 Webhook 等问题已有服务端护栏或统一实现；本报告不把基线发现继续写成当前已确认阻断项。

生产上线仍不能仅凭本轮沙箱结果放行。真实微信/支付宝/云闪付商户凭证不可用，生产协议、证书、异步通知、真实出款和真实账单下载尚未验证；这些能力必须经过独立的生产联调门禁。

## 6. 当前剩余风险与测试缺口

以下不是本轮已确认的 P0，而是进入真实商户联调前必须继续处理的项目：

1. **真实渠道协议未验收**：没有生产商户凭证、证书和真实回调，无法证明微信/支付宝/云闪付生产收单、退款、出款、分账、账单下载和证书轮换。
2. **四眼转账成功分支**：当前会话只有一个管理员，已验证自审批被禁用和驳回释放；需要第二个具备审批权限的用户完成“审批通过→渠道调用→核销”实测。
3. **失败 Outbox 重投**：本轮所有支付事件最终完成，没有通过页面制造失败事件；需要可控的失败 Fixture 验证重投、claim 和幂等。
4. **可恢复收银台**：微信扫码轮询已验证；支付宝/H5 离开页面后的 `returnUrl`、刷新恢复和多标签并发仍需真实浏览器联调。
5. **对账覆盖面**：当前沙箱账单覆盖订单金额/状态和 CSV 差异核验；退款、手续费、分账、转账、结算和真实渠道 CSV 模板仍需扩展。
6. **并发边界**：风控日限额、支付链接名额、退款/预占、结算 CAS 的高并发与重启恢复需要独立集成环境验证。
7. **生产能力门禁**：未实现的生产分账、代扣、预授权等操作必须继续保持明确拒绝，不能用沙箱成功响应替代。
8. **自动化验证**：按当前阶段要求暂不接入自动化测试；后续发布前仍应补 PostgreSQL/Redis 集成、协议 Fixture、权限矩阵和端到端回归。

## 7. 无历史兼容约束下的最优方案

后续重构以“支付意图、渠道尝试、提供方事件、不可变资金账本”为核心，而不是继续扩展单一订单表：

- `payment_intent`：租户、应用、业务键和金额的唯一支付意图；幂等键必须包含 tenant + application + bizType + bizId。
- `payment_attempt`：每次渠道尝试独立记录 `processing/unknown/succeeded/failed`，未知结果只能由查单或事件收敛。
- `provider_event_inbox`：先按 provider + merchant account + provider event id 去重落原始通知，再完成商户身份、金额、币种和应用绑定校验。
- `merchant_account`：把租户、渠道商户号、应用、环境、证书版本和 capability 绑定成不可混用的账户边界。
- 双分录 Journal：收款、手续费、退款、分账、预占、冻结、待结算、出款分别设科目；已过账凭证只追加冲正，不删除或改写。
- 所有退款、分账、转账、预授权、代扣和结算操作使用独立 operation id、预占、CAS 和未知结果收敛策略。
- capability registry 作为唯一方式来源，订单、链接、会员、业务示例和公开收银台统一消费；管理端启停状态与服务端能力必须同源。
- 公开收银台使用可恢复 cashier session，回跳携带会话标识，刷新/重开后恢复订单状态和轮询。
- Webhook 使用版本化签名、时间窗、SSRF/出口策略、租户/应用隔离、投递 attempt 和最终结果；沙箱与真实渠道复用同一状态机 Fixture。

## 8. 验收门槛与实施顺序

进入真实商户联调前，至少满足：

- 回调绑定唯一 merchant account，金额、币种、商户号、AppId 全部一致；
- 重复、乱序、并发回调只产生一次履约和一次账务结果；
- 所有查询、幂等、Webhook、对账、账户和结算接口通过租户隔离检查；
- 退款、分账、转账、结算均有余额预占、审批/风控和操作原因；
- 生产适配器未实现能力明确拒绝，绝不返回模拟成功；
- 沙箱可编排成功、失败、处理中、超时、未知、重复、乱序和金额不一致；
- 两管理员四眼审批、真实账单、证书轮换和回调重放完成联调；
- 自动化集成/E2E 测试进入 CI（本阶段按要求暂缓）；
- 20 个支付页面在 1280/1440 宽度无文本竖排、列遮挡和隐藏操作；
- 公开收银台在桌面、移动浏览器、微信内和支付宝回跳后均能恢复状态。

建议顺序：真实协议与沙箱 Fixture → Intent/Attempt/Inbox → 账本与 operation 状态机 → capability/收银台恢复 → 权限与并发集成验证 → 再开放生产商户。
